# Web security
## When it applies
Any bot, service or script that receives HTTP requests from outside (Slack, GitHub, Linear, Gmail push, Google Calendar push, generic webhooks, scheduled triggers), signs in to third-party APIs with OAuth, stores tokens or API keys, or fetches URLs on behalf of a user. Applies in full when the receiver runs on the owner's machine with the owner's credentials. For the agent-specific side (prompt injection, tool approval), see `ai-agent-security.md`.
## Standards
- **Slack request signing (v0)**: Verify `X-Slack-Signature` = `v0=` + hex HMAC-SHA256 of `v0:{X-Slack-Request-Timestamp}:{raw body}` with the app signing secret, compare in constant time, and reject any timestamp more than 5 minutes from your clock. Why: stops forged and replayed requests; the body must be the raw bytes, not re-serialized JSON. Source: https://docs.slack.dev/authentication/verifying-requests-from-slack
- **GitHub webhook signature**: Verify `X-Hub-Signature-256` (`sha256=` + HMAC-SHA256 of the raw body with the webhook secret) using a constant-time compare such as `hmac.compare_digest` or `crypto.timingSafeEqual`; never use `X-Hub-Signature` (SHA-1) or plain `==`. Why: anyone who knows the URL can post fake events otherwise. Source: https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries
- **Linear webhook signature**: Verify `Linear-Signature` (hex HMAC-SHA256 of the raw body, signed with the webhook signing secret) and check the timestamp (`Linear-Timestamp` header, or `webhookTimestamp` in the body, as Linear documents) is within 1 minute of your clock. Why: Linear recommends exactly this to guard against replay. Source: https://linear.app/developers/webhooks
- **Standard Webhooks (for generic and custom webhooks)**: Use `webhook-id`, `webhook-timestamp`, `webhook-signature` headers; signed content is `{id}.{timestamp}.{body}`, HMAC-SHA256 with a base64 secret (`whsec_` prefix), signature sent as `v1,<base64>` (space-separated list during key rotation); check the timestamp tolerance and try each signature until one matches. Why: one vetted scheme beats a homemade one when you define your own webhooks. Source: https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md
- **Replay and idempotency**: Treat the delivery id (`webhook-id`, `X-GitHub-Delivery`, `Linear-Delivery`, Slack `event_id`) as an idempotency key and store it for at least the tolerance window; acknowledge fast, do the work async. Why: providers retry and attackers replay; a job must not run twice. Source: https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md
- **Fail closed on verification**: Missing secret, missing header, bad signature or stale timestamp returns 401/403 and runs nothing; verify before parsing or logging the body. Why: a verification that can be skipped is not verification. Source: https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html
- **OAuth 2.0 Security BCP (RFC 9700)**: Use the authorization code flow with exact redirect-URI string matching; public clients MUST use PKCE; do not use the implicit grant or password grant; prefer sender-constrained or short-lived access tokens and rotate refresh tokens. Why: this is the current IETF baseline and closes code injection and token leakage. Source: https://www.rfc-editor.org/rfc/rfc9700
- **PKCE (RFC 7636)**: Send a fresh random `code_verifier` per request and the S256 `code_challenge`; never use `plain` unless S256 is impossible. Why: a stolen authorization code is useless without the verifier. Source: https://www.rfc-editor.org/rfc/rfc7636
- **OAuth for native and loopback apps (RFC 8252)**: Use the system browser, not an embedded web view; redirect to a loopback IP literal (`http://127.0.0.1:{port}/path` or `http://[::1]:{port}/path`) on an ephemeral port, together with PKCE; validate `state`; do not ship a client secret in a local app. Why: a local bot is a native app; embedded views expose credentials. Source: https://www.rfc-editor.org/rfc/rfc8252
- **Least-privilege scopes**: Request the smallest scopes and token type per integration (read-only where possible, one repo or channel over whole org, fine-grained GitHub tokens or app installs, Slack bot scopes only), and review them when features change. Why: a leaked or abused token can only do what its scopes allow. Source: https://www.rfc-editor.org/rfc/rfc9700 (section 2.3, privilege restriction)
- **Secret storage**: Keep secrets out of source, chat, logs and images; load from the OS keychain (Windows Credential Manager / DPAPI, macOS Keychain, libsecret) or a secrets manager, with a gitignored `.env` only as the minimum; one secret per integration; rotate on a schedule and immediately after any exposure. Why: the owner's machine holds powerful credentials, so a single leak is a full takeover. Source: https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html
- **Rate limiting and body limits**: Rate-limit per source and per verified identity, cap request body size and job concurrency, and queue jobs. Why: signature checks cost CPU, and each chat job costs money and runs code; floods must not become DoS or a bill. Source: https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/
- **SSRF prevention for outbound fetches**: Fetch only from an allowlist of hosts when possible; otherwise resolve DNS and block private, loopback, link-local and cloud metadata ranges (including 169.254.169.254) on the resolved IP, disable redirect following or re-validate each hop, allow only http/https. Why: a URL in chat or a webhook can point the bot at internal services and local files. Source: https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html
- **OWASP ASVS 5.0 (released May 2025)**: Pick a target level (L1 for any internet-facing endpoint; L2 for anything holding the owner's credentials or acting on their data, which includes these bots), and map the web-service, API, OAuth, token and secrets chapters to checks in the spec. Why: ASVS gives testable requirements instead of "be secure"; levels are cumulative. Source: https://github.com/OWASP/ASVS
- **Logging without secrets**: Log delivery id, source, event type, verification result, job id and who acted; never log tokens, signing secrets, authorization codes, full headers or raw bodies that may contain them; redact before writing and cap log retention. Why: logs are copied and read widely; a token in a log is a leaked token. Source: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- **TLS and exposure of local receivers**: Expose a local receiver only through an authenticated tunnel or reverse proxy with HTTPS, bind to localhost by default, and publish only the webhook path. Why: the receiver is on a personal machine; a wide-open port is a way into it. Source: https://github.com/OWASP/ASVS
